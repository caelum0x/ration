### 1. [fix] Bridge-grant holds now release on repayment (`700b6e8`)
`services/card-issuance/internal/bridge/service.go`'s HOLD reference changed from `bridge:<hold_id>` to `bridge:<deposit_id>:<hold_id>`, so `services/ledger-core/src/ledger.rs`'s `mark_deposit_received_with_entry` can find and atomically RELEASE every outstanding bridge HOLD tied to the deposit that just settled, in the same WAL frame as the credit. Verified via the existing `TestRationBridgeFunding_VelocityCapAllowsAfterRepayment` test and live, later in the round, via the circuit-breaker fallback actually granting a second time after repayment.

### 2 & 3. Tenant-scoped authorization everywhere, including ledger-core itself (`eef5f6b`, `ed0dbe1`, `a515e13`)
- `proto/auth.proto`: added `is_operator` to API keys/JWTs.
- `services/cli`, `services/tui`, `services/agent` each mint an operator-scoped credential at startup and attach it to every gateway call. `RATION_GATEWAY_REQUIRE_TENANT_AUTH` now defaults to `true`.
- New `services/gateway/internal/cardtenant`: resolves `card_id` → `tenant_id` so `GetCard`/`AdjustCardLimit` are no longer unscoped.

- **The big one**: `services/ledger-core/src/tenantauth.rs` + `src/authclient.rs` — ledger-core now verifies every tenant-scoped (or operator-only) caller's own credential directly, closing THREAT-MODEL.md's "the biggest one" sub-gap (cli/tui/agent/gateway/card-issuance/webhook-ingestion/tenant-registry all dial ledger-core directly, bypassing gateway's tenantauth entirely). `RATION_LEDGER_REQUIRE_TENANT_AUTH` defaults to `true`; ledger-core refuses to start if that's true with no `AUTH_GRPC_ADDR` reachable. Every direct ledger-core caller (gateway, card-issuance, webhook-ingestion, tenant-registry) got a new `internal/authclient` to mint its own operator credential.
- Verified live: full seed → simulate-deposit → agent poll → bridge-funding cycle, zero `Unauthenticated`/`PermissionDenied` anywhere in any service's logs.

### 10. LLM circuit breaker (`9c859de`)
New `services/agent/internal/llm/breaker.go`: trips after N consecutive failures within a rolling window, short-circuits to `ErrCircuitOpen`, one half-open trial before fully closing. `internal/loop.Runner` treats a tripped breaker as "execute the deterministic hard-rule envelope directly" (same tool-handler code path, canned text) rather than skipping the tick. **Verified live**: with no `ANTHROPIC_API_KEY` configured, the breaker tripped after 3 failures and then executed real bridge-funding grants (HOLD entries landing on ledger-core, held balance increasing) via the fallback path.

### [fix] Velocity cap no longer blocked by a grant that never executed (`3376017`)
Found live while verifying the breaker fallback above: the unconditional "envelope pre-check" decision recording (before the LLM is even attempted) got counted by `hasOpenGrantWithinWindow` as "an open unrepaid grant" even when the real tool call never ran — permanently velocity-capping a deposit whose first attempt merely failed transiently. Fixed with a `wasActuallyGranted` check (only a decision snapshot containing `granted_minor_units`, which only a real executed grant's snapshot has, counts).

### 12. Automated dev-CA cert rotation (`9dca6d1`)
New `scripts/rotate-dev-ca.sh` + `services/auth/cmd/issue-service-cert` client for `IssueServiceCert`. Point `auth`'s `AUTH_CA_CERT_FILE`/`AUTH_CA_KEY_FILE` at the same static dev CA every service already trusts, and rotation issues fresh leaves against that identical root — no new CA to redistribute. **Verified live**: generated a CA, started `auth` against it, rotated all 10 service identities, confirmed new serials, matching keys, and `openssl verify -CAfile` passes.

### 11. Encryption at rest — WAL done, SQLite column-level NOT done (`cb87e97`)
New `services/ledger-core/src/wal_crypto.rs`: AES-256-GCM, wired into `append_and_commit`/`replay_wal_into_index` so every WAL frame is ciphertext before `wal_ffi::Wal::append` ever sees it — zero changes to the C WAL's frame format/CRC/recovery logic, since that layer already treats a payload as an opaque `&[u8]`. Opt-in via `RATION_LEDGER_ENCRYPTION_KEY`; disabled (unchanged plaintext behavior) by default. **Verified live**: the on-disk WAL file is genuine ciphertext (not valid JSON, no plaintext tenant names), a full seed/deposit/bridge-funding cycle runs correctly against an encrypted ledger, two new tests prove a real restart-and-recover round trip and loud failure on a wrong key.

**Remaining from item 11**: column-level encryption of SQLite's sensitive free-text fields (`deposit.external_ref`, `ledger_entries.reference`/`memo`, `agent_decisions.trigger`/`rationale`/`policy_snapshot_json`) was planned but not implemented this round — stopped short of it after a transient disk-full event on the build machine (unrelated to this change; recovered on its own) made me unwilling to start another multi-file refactor of the ledger's core read paths without full headroom to verify it thoroughly. The WAL is the system's actual source of truth and is now fully encrypted; the SQLite index is explicitly "a rebuildable, queryable index over it" (see `lib.rs`'s own doc comment) — a real but secondary exposure if the SQLite file leaks in isolation. Real, scoped next step for round 2: thread `Option<&wal_crypto::Key>` through `deposit.rs`/`agent_decision.rs`/the `ledger_entries` functions in `ledger.rs`, encrypting only those free-text columns (never `tenant_id`/amounts/timestamps/enums, which every query filters or sorts on).

### 1. SQLite column-level encryption (`a6aad08`)

`deposit.external_ref`, `ledger_entries.reference`/`memo`, and
`agent_decisions.trigger`/`rationale`/`policy_snapshot_json` are now
encrypted with the same `RATION_LEDGER_ENCRYPTION_KEY`/AES-256-GCM
`wal_crypto::Key` that already encrypts the WAL — `wal_crypto::
encrypt_opt`/`decrypt_opt` are the two new shared helpers every
read/write path in `deposit.rs`/`agent_decision.rs`/the
`ledger_entries` functions in `ledger.rs` goes through.
`ledger_entries.reference` was the one column in that list a real query
filtered on (`list_outstanding_bridge_holds_for_deposit`'s bridge-hold-
release matching, `bridge:<deposit_id>:*`): since AES-GCM ciphertext
can't support `LIKE`/`=` in SQL, that lookup now fetches by the
(unencrypted) `tenant_id`/`entry_type` pair — still covered by the
existing index — and matches the decrypted `reference` in Rust. Two new
tests (`bridge_hold_release_matches_by_reference_with_encryption`/
`_without_encryption`) prove that refactor didn't change behavior
either way. `cargo test`: 70/70 (51 lib incl. 7 new, 19 integration),
up from round 1's 44 baseline, 0 regressions. `cargo clippy`/`cargo
fmt` clean.

**[fix] found live, same commit**: `wal_crypto::Key::from_env()`
treated `RATION_LEDGER_ENCRYPTION_KEY` set to an empty string the same
as a real (but wrong-length) key, crashing ledger-core at startup with
`WrongKeyLength(0)` — and empty-but-set is exactly what
`.env.example`'s `RATION_LEDGER_ENCRYPTION_KEY=` line produces once

default judge path (`make build && scripts/run-demo.sh`, no env
changes) could not start ledger-core at all before this fix. Found by
actually running that exact path live while verifying the encryption
feature above, not by code review. Fixed to treat empty the same as
unset, matching `main.rs`'s own `auth_grpc_addr.is_empty()` check one
function away.

Verified live, twice: a full `scripts/run-demo.sh` → `ration seed` →
`ration simulate-deposit --late` → agent poll → partial bridge grant →

### 2. docker-compose.yml: `AUTH_GRPC_ADDR` missing for ledger-core (`83916f8`)

Found while preparing a real containerized deployment target (see item
4 below): ledger-core's compose entry never set `AUTH_GRPC_ADDR`, so
the container-network default resolved to ledger-core's own loopback,
not `auth`'s. `RATION_LEDGER_REQUIRE_TENANT_AUTH` defaults to true and

real tenant-scoped RPC then failed its credential check — a plain
`docker compose up --build` of this repo, as committed through round 1,
was silently non-functional beyond a bare health check.
`scripts/run-demo.sh` never hit this (same host, so `localhost:7010`
really is `auth`). Fixed with the same explicit service-name override
every other direct ledger-core caller in the compose file already has.
